# ECS X-Ray connections

ECS → X-Ray (`traces_to`) adds a task-local OpenTelemetry collector, regional upload permissions, and native trace-group membership. The editor discovers the connection through `/api/connection-schemas`. `EmptyConnectionConfig` adds no editable connection fields; configure task sizing/placement on the ECS node and the additional predicate/Insights settings on the X-Ray node.

The modeled Linux Fargate task receives one nonessential `iac-xray-collector` container using `public.ecr.aws/aws-observability/aws-otel-collector:v0.49.0`. It reserves 64 CPU units and 256 MiB, uses task credentials, and reads its configuration from `AOT_CONFIG_CONTENT`. Diagnostic logs belong to the ECS module at `/aws/ecs/<node>/xray`, with 30-day retention. The [pinned ADOT release](https://github.com/aws-observability/aws-otel-collector/releases/tag/v0.49.0) includes the OTLP receiver, ECS resource detector, attributes processor, and X-Ray exporter used here; upgrade the implementation and runtime verification together.

OTLP listeners bind only to `127.0.0.1:4317` for gRPC and `127.0.0.1:4318` for HTTP. No collector port mapping or ingress rule is generated. Caller-supplied containers receive these connection-owned settings:

| Environment variable | Value |
| --- | --- |
| `OTEL_TRACES_EXPORTER` | `otlp` |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `http://127.0.0.1:4318/v1/traces` |
| `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` | `http/protobuf` |

These settings replace existing entries with the same names, while preserving other environment variables, application service names, secrets, mounts, and container properties. Signal-specific endpoint settings include the complete `/v1/traces` path and take precedence over generic exporter settings, following the [OpenTelemetry exporter specification](https://opentelemetry.io/docs/specs/otel/protocol/exporter/). Application images still need compatible SDK/agent instrumentation and must honor these settings. No application binary, tracing library, sampling policy, legacy UDP daemon, or sampling proxy is installed. Existing SDK sampling and context-propagation choices remain application concerns. The pinned collector accepts both AWS-style and ordinary W3C trace IDs; [X-Ray segment documents](https://docs.aws.amazon.com/xray/latest/devguide/xray-api-segmentdocuments.html) describe the converted ID format.

The trace pipeline applies memory limiting, ECS resource detection, an attributes processor, and batching before X-Ray export. The attributes processor upserts `iac_ecs_cluster_arn` on every span using the native `aws_ecs_cluster` ARN. It replaces any incoming value of that reserved annotation. The exporter indexes this attribute, preserves application service names, disables automatic indexing of all attributes, and disables daemon telemetry. See the pinned [X-Ray exporter configuration](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.156.0/exporter/awsxrayexporter) and [attributes processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.156.0/processor/attributesprocessor).

One source-owned inline policy grants only `xray:PutTraceSegments`, with wildcard resources restricted by `aws:RequestedRegion` to the task module's provider Region. X-Ray groups cannot scope this upload action; see the [X-Ray authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_xray.html). No sampling reads, telemetry writes, group mutation, or encryption administration are granted. The existing ECS-owned role serves as task and execution role; application containers share its upload permission. Its existing image/log permissions and other connection policies remain composed. Task creation explicitly depends on the tracing policy.

Each connected group receives a typed `xray_ecs_clusters` map containing native cluster ARNs and names. Its member selectors use `annotation.iac_ecs_cluster_arn = "<native-cluster-arn>"`, combined with `OR`. When Lambda producers share the group, their service/function selectors join the same union. The union is combined with the configured predicate using `AND`; the default `responsetime > 5` therefore keeps only slow matching traces. Blank predicates and reserved group names are rejected; AWS checks predicate syntax during deployment. [X-Ray filters](https://docs.aws.amazon.com/xray/latest/devguide/xray-console-filters.html) define query/group membership, without isolating readers or constraining upload permissions.

Multiple ECS nodes can share a group, and one task can belong to multiple groups. The collector exports once to regional X-Ray rather than duplicating spans for each group. Duplicated connections are idempotent and membership ordering is deterministic. Native guards check cluster ARN/name consistency, common account/partition/Region, group names/predicates, and valid Insights notifications. The group depends on native cluster outputs; the source never depends on group outputs, avoiding cycles. Grafana queries consume the effective native filter through the existing outputs. The group exports `trace_filter_expression`; each ECS node exports `xray_collector_configuration` and `xray_collector_log_group`.

Tracing defaults an unset launch type to Fargate and uses platform `LATEST`. Subnet and security-group placement can come from external IDs or managed connections. Task guards reject the reserved collector name, insufficient declared capacity, conflicting TCP port mappings/ranges, and secrets overriding the three tracing environment variables, including connection-injected secrets. [ECS port mappings](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_PortMapping.html) support ranges, which are checked alongside individual ports. Applications must also leave these ports unbound when no mapping declares them.

The existing Prometheus collector remains independent. With both connections, the two sidecars reserve a total of 128 CPU units and 512 MiB; combined capacity guards include application reservations. Prometheus application scraping cannot use ports 4317/4318. Secret injection and EFS mounts are composed before tracing environment settings and sidecars, so collectors receive neither application secret bindings nor mounts. Removing a connection removes its collector, policy, diagnostic logs, and managed selectors from regenerated Terraform; preserve logs separately when required.

Before deployment, supply real application images/instrumentation, appropriate task sizing, a nonzero desired count, and network access for public image pulls, Logs, and X-Ray. Private ECR endpoints alone cannot pull the public collector image. Configure network rules, any customer-managed X-Ray encryption, quotas, costs, and dashboards separately. Local tests evaluate emitted HCL/YAML, validate provider schemas and dependency graphs, and send real OTLP traffic through the pinned collector to a loopback AWS mock. They do not deploy resources or verify live AWS ingestion.
