# EKS Prometheus connections

EKS → Managed Prometheus (`sends_metrics`) creates an AWS-managed scraper for each cluster/workspace binding. The editor discovers the connection through `/api/connection-schemas`. `EksPrometheusConfig` exposes `scrape_interval_seconds`, an integer defaulting to 60 with an editor range of 30–3600. Duplicate bindings share one scraper; conflicting intervals are rejected. Multiple destinations create independent scrapers, and multiple clusters can share a workspace.

The EKS module owns `aws_prometheus_scraper`, the default-configuration data source, and a VPC DNS lookup. A typed destination map receives native workspace ARNs through module inputs. The scraper inherits the native cluster ARN, all cluster subnet IDs, and the automatically created cluster security group. Subnet/VPC placement connections therefore compose without copied identifiers. Workspace modules remain independent of scraper modules, and connected workspaces include the `AMPAgentlessScraper` tag AWS adds. This follows the [provider's workspace tag guidance](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/prometheus_scraper).

The connection defaults unset EKS `authentication_mode` to `API_AND_CONFIG_MAP` and unset `endpoint_private_access` to true. Explicit `CONFIG_MAP` authentication or disabled private access is rejected. Compatible explicit API authentication is retained. Both fields are optional service settings; standalone clusters preserve their previous rendering when unset. Public endpoint settings are preserved. **Enabling EKS API authentication cannot be reversed on an existing cluster.** Review the generated change and existing cluster access before applying; `API_AND_CONFIG_MAP` retains the existing `aws-auth` access mechanism. See [EKS authentication migration](https://docs.aws.amazon.com/eks/latest/userguide/setting-up-access-entries.html).

After deploying collection, set the cluster's authentication mode explicitly to its deployed API-enabled mode before removing the connection and regenerating Terraform. Otherwise the unconnected generator omits the access block, and Terraform's default can attempt an unsupported return to `CONFIG_MAP`. Set private endpoint access explicitly too if it should remain enabled after connection removal. Connection-derived settings affect the generated project, without rewriting the saved diagram's service configuration.

Terraform preconditions verify API authentication, private access, two to five native subnets, VPC DNS support/hostnames, workspace ARN shape, identical native partition/account/Region, and integer interval bounds. EKS cluster creation itself requires subnets in at least two Availability Zones. Clusters using more than five subnets require a separately configured collector; this connection uses the complete native subnet set. Explicitly different provider Regions are rejected when both are supplied; native checks also catch deployment placement and module overrides. The deployment identity needs VPC describe access for the DNS lookup. Network ACLs, routes, restrictive cluster security-group rules, and metrics endpoints must allow collection. See [AWS managed collector setup](https://docs.aws.amazon.com/prometheus/latest/userguide/AMP-collector-how-to.html) and [scraper source limits](https://docs.aws.amazon.com/prometheus/latest/APIReference/API_EksConfiguration.html).

`aws_prometheus_default_scraper_configuration` supplies AWS's current default jobs. The generator decodes that YAML, changes only `global.scrape_interval`, preserves other global settings and jobs, and re-encodes plaintext YAML. Provider/API blob encoding is handled by the provider. Collection creates no in-cluster agent or Kubernetes resources. Compatible workload annotations and exposed metrics endpoints, worker capacity, and metrics network reachability remain operational prerequisites; this does not configure application instrumentation. See [default configuration data source](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/data-sources/prometheus_default_scraper_configuration).

AWS creates the scraper service-linked role and automatically establishes EKS access for API-enabled clusters. Terraform does not also manage those roles or access entries. The deployment identity needs permissions to manage scrapers, retrieve the default configuration, create the service-linked role, and manage EKS access as required by AWS. Service availability and scraper quotas apply; each binding incurs collector costs. Collectors are independent, and this connection does not configure high-availability deduplication. See [AWS service-linked role ownership](https://docs.aws.amazon.com/prometheus/latest/userguide/using-service-linked-roles.html).

The cluster module exports `prometheus_scrapers`, keyed by workspace node name, containing scraper ID, ARN, AWS-owned role ARN, and destination workspace ARN. For a cluster node named `cluster`, inspect the generated environment's output:

```sh
terraform output -json cluster > cluster-outputs.json
jq '.prometheus_scrapers' cluster-outputs.json
```

Apply the generated Terraform to create collection. Check scraper status and workspace metrics after provisioning; local validation cannot verify live endpoint reachability or ingestion. A workspace connected to [Managed Grafana](backend-grafana-prometheus-connections.md) can query those metrics once its exported data-source settings are applied in Grafana. Dashboards and alerts remain separately configured. [EFS storage connections](backend-efs-connections.md) still configure the CSI add-on and export storage manifests for manual application.
