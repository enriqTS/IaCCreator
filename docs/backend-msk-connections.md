# MSK topic access connections

Lambda and ECS support `reads_from` and `writes_to` connections to provisioned MSK clusters. Both require a concrete existing `topic_name`; reads additionally require a `consumer_group`. Names use a conservative subset of Kafka names: 1–249 ASCII letters, digits, dots, underscores, or hyphens, beginning with a letter or digit. Wildcards, paths, and internal topic names are excluded. Reads are the default connection type.

The connection enables SASL IAM authentication, disables unauthenticated access, and configures TLS for both client/broker and inter-broker traffic. Existing unauthenticated clients must migrate. Set an explicit Kafka version meeting the 2.7.1 minimum; the version must also be available in the deployment Region. Generation and Terraform lifecycle conditions check the minimum, not AWS version availability. No automatic version upgrade, SASL/SCRAM secret, or certificate authentication is configured.

The MSK node now exposes `broker_instance_type`, `subnet_ids`, and `security_group_ids` and emits the required `broker_node_group_info`. Connections require two or three distinct subnet IDs, at least one security group, and a positive broker count divisible by the subnet count. Terraform preconditions guard these invariants when variables are overridden. Subnets must actually belong to the required distinct availability zones in one VPC; Region, broker-type, and capacity restrictions remain AWS deployment prerequisites. External identifiers are preserved. Network connections, security-group rules, routes, public endpoints, and multi-VPC access are not created by topic connections.

Permissions attach to the Lambda execution role or ECS task role:

| Scope | Read connection | Write connection |
| --- | --- | --- |
| Exact cluster ARN | Connect, DescribeCluster | Connect, DescribeCluster |
| Exact topic ARN | DescribeTopic, ReadData | DescribeTopic, WriteData |
| Exact consumer-group ARN | DescribeGroup, AlterGroup | None |

All actions use the `kafka-cluster:` prefix. Topic and group ARNs derive from the cluster's native ARN by replacing its resource-type segment and appending the validated name; partition, Region, account, cluster name, and UUID are retained. No topic, group, cluster, or transactional-ID wildcard is granted. Group access permits joining and committing offsets, not group deletion. Topic creation, deletion, configuration changes, and transactions are excluded. See [AWS MSK action dependencies and resource formats](https://docs.aws.amazon.com/msk/latest/developerguide/kafka-actions.html).

Producer connections are explicitly **non-idempotent**: configure `enable.idempotence=false` and omit `transactional.id`. This can permit duplicate records during retries; handle duplicates in the application where needed. No `WriteDataIdempotently` or transactional-ID permissions are added. Many clients otherwise enable idempotence by default. See [AWS's idempotent-write permission considerations](https://docs.aws.amazon.com/msk/latest/developerguide/create-iam-access-control-policies.html).

Consumers export `msk_<cluster-node-name>_<hash>` objects containing the topic name, private IAM bootstrap broker string, Region, `security_protocol=SASL_SSL`, and `sasl_mechanism=OAUTHBEARER`. Reader objects include `group_id`; writer objects include `enable_idempotence=false`. Application code must configure an IAM token provider using runtime AWS credentials and translate these metadata keys to its Kafka client's configuration. These outputs do not install a signer library, deploy application code, or inject environment variables. No credentials or tokens are generated by Terraform.

Topics must be provisioned separately. Cluster resource policies for cross-account access and any existing broader IAM grants remain externally managed. Kafka ACLs do not constrain IAM identities; use IAM policies for their authorization. See [AWS MSK IAM access control](https://docs.aws.amazon.com/msk/latest/developerguide/iam-access-control.html). Lambda connections grant direct client access; Lambda event-source mappings remain a separate roadmap item.

Repeated connections share native authentication settings and common outputs. Topic, group, and access-mode selections produce distinct client bindings; ordering and duplicate connectors do not change the generated project. Terraform validation covers syntax, provider schema, and dependency graphs; it does not verify network reachability or perform Kafka operations.
