# CloudTrail CloudWatch Logs delivery

CloudTrail → CloudWatch (`logs_to`) sends account-trail events to the connected log group through native `cloud_watch_logs_group_arn` and `cloud_watch_logs_role_arn` arguments. The connection uses the typed empty config and is discovered through `/api/connection-schemas`. Each trail accepts one managed log group; repeated connectors share its delivery resources. Multiple trails can use the same group, with one independent role per trail.

The trail module owns `cloudwatch_logs.tf`, containing provider identity data sources, an `aws_iam_role`, and one inline `aws_iam_role_policy`. The role trusts the partition's CloudTrail service principal. Its policy grants CreateLogStream and PutLogEvents only on the selected group and current account's CloudTrail stream prefix. Single-Region trails restrict the stream Region; multi-Region trails permit all CloudTrail Region prefixes for that account. Provider-generated IAM name suffixes avoid collisions between environments. The module exports `cloudwatch_logs_role_arn`.

The log-group ARN crosses the module boundary as an input. CloudTrail receives exactly one trailing `:*`, as required by the provider, and waits for the role's policy before creation. Native lifecycle guards reject malformed log-group ARNs and require the same partition, home Region, and account as the trail provider. Backend validation checks effective Regions in every environment, including environment overrides and implicit project defaults.

Encrypted destinations reuse `KmsConsumerGrants` to authorize the delivery role on the selected key. These role permissions are constrained by `kms:ViaService` to the regional CloudWatch Logs service. Managed keys use native ARN inputs; external key IDs and aliases resolve through a key data source without fetching secrets. The key owner must also authorize Logs in its key policy; managed KMS → CloudWatch relationships already install that policy. CloudTrail's own S3-log encryption remains a separate KMS relationship. Shared keys retain one policy owner and pre-creation identities, so these delivery paths do not create dependency cycles.

CloudWatch delivery supplements CloudTrail's required S3 destination. Connect CloudTrail → S3 to manage its bucket delivery policy, or configure an external bucket and its policy. Preview warns when the S3 destination is missing and reports external-key prerequisites. The deployment identity needs permissions to create/pass the generated role. Log retention and class stay under the log group's existing configuration. Metric filters, alarms, organization-trail settings, and log-reader permissions are separate concerns. Unconnected trails emit no CloudWatch delivery resources or attributes.

The implementation follows [AWS CloudTrail CloudWatch delivery](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/send-cloudtrail-events-to-cloudwatch-logs.html), [delivery-role permissions](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-required-policy-for-cloudwatch-logs.html), [CloudTrail stream naming](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudwatch-log-group-log-stream-naming-for-cloudtrail.html), [CloudWatch KMS caller permissions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/encrypt-log-data-kms.html), and the [Terraform CloudTrail schema](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/cloudtrail).
