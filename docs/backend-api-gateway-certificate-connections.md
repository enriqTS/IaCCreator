# Certificate Manager → API Gateway

The `secures` connection creates an API-owned Regional custom domain and maps it to a generated stage using the connected ACM certificate. It supports the modeled HTTP and WebSocket APIs with TLS 1.2. The connection exposes three settings:

| Setting | Behavior |
|---|---|
| `domain_name` | Required DNS hostname covered by the certificate's primary name or SANs; normalized to lowercase. A leading wildcard is supported for public certificates. |
| `stage_name` | Empty selects the first configured stage. An HTTP API without configured stages gets an automatically deployed `$default` stage. Explicit names must select a generated stage. |
| `api_mapping_key` | Empty maps the domain root. HTTP mappings support paths such as `orders/v1`; WebSocket mappings support one path segment. Paths preserve case and reject surrounding slashes, empty segments, unsupported characters, and lengths over 300. |

The API module owns `aws_apigatewayv2_domain_name` and `aws_apigatewayv2_api_mapping` in `certificate_domains.tf`. Domain and mapping identifiers include hashes of their hostname/path, preserving distinctions such as `v1-orders`, `v1_orders`, and `v1/orders`. Several paths can share one hostname and certificate, and each path can select a different stage. Several hostnames can use the same certificate. Identical duplicate connections are idempotent, and generated output does not depend on connector order.

Each hostname has one owning API module and one certificate per effective Region. Different API modules cannot independently create the same Regional hostname; a separately modeled domain resource would be needed to share ownership across APIs. A hostname with an existing manually configured `custom_domain` also cannot be created by a connection. Manual domains with other names are preserved. The same hostname/path cannot select conflicting stages or certificates. Stage names that collide after Terraform identifier sanitization are rejected.

The certificate module exports `issued_certificate_arn` and `api_gateway_certificate_names`, using the native certificate domain and SANs. The API receives these through typed ARN and `list(string)` inputs. Public requests own one `aws_acm_certificate_validation` waiter in `certificate_issuance.tf`, shared with other API domains and Client VPN consumers. Existing VPN-specific outputs remain available. Complete DNS or email validation before the waiter can create the domain; this connection does not create validation records.

Private CA → Certificate Manager (`issues_certificate`) composes with concrete API custom domains independently of connector order. These native private requests need no public validation waiter, and clients must trust the issuing root. Private-certificate wildcard domains and private-certificate mutual TLS are rejected; the latter requires an additional public ownership-verification certificate, which this connection does not model.

Backend validation checks hostname coverage, certificate and API effective Regions, selected stages, Regional endpoint type, TLS 1.2, and ownership conflicts. Certificate wildcards cover exactly one DNS label and do not cover the zone apex. Domain lifecycle preconditions repeat coverage checks using native certificate names and verify ARN Region/account against the API provider, catching Terraform variable overrides.

Public-certificate HTTP domains preserve the API's external `mutual_tls_truststore_uri` and optional version fields. The URI must identify an S3 bucket and object. Structured truststore dictionaries, versions without a URI, and WebSocket mutual TLS are rejected for managed domains. If mutual TLS should control all API access, disable the default execute-api endpoint; preview reports this requirement. Truststore uploads, client credentials, and ownership-verification certificates remain separate work.

WebSocket APIs require a configured named stage with automatic deployment disabled. This connection maps the stage without creating or attaching API deployments. Deploy WebSocket routes and integrations to that stage separately. HTTP stages configured without automatic deployment also require a separate deployment. Existing Cognito JWT authentication and Lambda route connections compose with the generated domain and mapping.

Domain outputs expose the hostname, ARN, target domain, and hosted-zone ID under each deterministic domain resource prefix. Configure a DNS CNAME or Route 53 alias to reach the endpoint. API routes and integrations remain application configuration. Preview lists owned domains/mappings and the shared issuance waiter, with DNS, trust, and deployment prerequisites. No workload IAM grants or private-key exports are generated.

The implementation follows the [Terraform custom-domain schema](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/apigatewayv2_domain_name), [API mapping schema](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/apigatewayv2_api_mapping), [stage schema](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/apigatewayv2_stage), [HTTP domain requirements](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-custom-domain-names.html), [HTTP mapping rules](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-mappings.html), [WebSocket mapping rules](https://docs.aws.amazon.com/apigateway/latest/developerguide/websocket-api-mappings.html), and [mutual TLS prerequisites](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-mutual-tls.html).
