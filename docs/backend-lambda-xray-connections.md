# Lambda X-Ray connections

[ECS X-Ray connections](backend-ecs-xray-connections.md) can share the same group. Independent producer selectors join a single `OR` union before the configured group predicate is applied with `AND`; native membership guards remain specific to each producer.

Lambda → X-Ray (`traces_to`) enables `Active` tracing and selects the connected functions in an X-Ray group. The editor discovers the connection through `/api/connection-schemas`; its `EmptyConnectionConfig` has no editable fields. Use the Lambda node's existing tracing setting and the X-Ray node's existing filter and Insights settings.

An unset tracing mode becomes `Active`. An explicitly configured `PassThrough` mode is rejected, as are Lambda layers. [Lambda active tracing](https://docs.aws.amazon.com/lambda/latest/dg/services-xray.html) creates service and function segments for sampled invocations. The connection does not add an ADOT layer, extension, application SDK, or custom sampling rule. Published versions retain their tracing configuration; publish and route to a suitable version when changing a deployed function's tracing behavior. Kafka/MSK, MQ, and DocumentDB event-source invocations do not support this tracing integration.

Each connected function owns one additional inline policy on its existing execution role. It grants only `xray:PutTraceSegments` and `xray:PutTelemetryRecords`, with `Resource = "*"` and an `aws:RequestedRegion` condition derived from the function module's provider. These upload actions use wildcard resources; an X-Ray group ARN cannot act as their destination boundary. See the [X-Ray authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_xray.html). The [AWS daemon policy](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSXRayDaemonWriteAccess.html) also contains sampling reads, which this connection does not need or grant. The function explicitly depends on both its existing base policy and the upload policy.

The group receives a typed `xray_lambda_functions` map containing native function ARNs and names. For each function, the generated filter selects both `AWS::Lambda` and `AWS::Lambda::Function` nodes by name, type, and account. Member selectors are combined with `OR`, then combined with the configured group predicate using `AND`. [X-Ray filter syntax](https://docs.aws.amazon.com/xray/latest/devguide/xray-console-filters.html) supports these typed identities and compound expressions. For a function named `checkout`, the effective filter is:

```text
((service(id(name: "checkout", type: "AWS::Lambda", account.id: "123456789012")) OR service(id(name: "checkout", type: "AWS::Lambda::Function", account.id: "123456789012")))) AND (responsetime > 5)
```

The default `responsetime > 5` therefore keeps only slow matching traces. Change the group predicate when broader coverage is intended; blank predicates are rejected. AWS validates the predicate's X-Ray syntax during deployment. Groups select traces and associated graphs/metrics; group membership does not isolate trace readers or constrain uploads.

Multiple functions can share a group, and one function can belong to multiple groups while retaining one upload policy. Duplicate bindings are idempotent and membership order is deterministic. Native names are JSON-encoded in the filter, so diagram-node names never replace deployment identities. Terraform guards check unqualified function ARN syntax, name consistency, common account/partition/Region, concrete non-reserved group names, nonempty predicates, and valid Insights notification settings. The function also checks that module overrides retain `Active` tracing. Notifications require Insights, matching [CreateGroup](https://docs.aws.amazon.com/xray/latest/api/API_CreateGroup.html).

The group depends on its functions through module inputs. Functions and their policies do not depend on group outputs, avoiding a dependency cycle. Existing logging, secret-access policies, and dead-letter settings remain composed. A connected Grafana workspace reads the group's effective native filter through its existing query settings. The group also exports `trace_filter_expression` in the generated environment's node outputs.

Deployment still requires valid function code, suitable invocation traffic, AWS API reachability, and any application instrumentation or customer-managed X-Ray encryption setup. Sampling, service availability, quotas, and tracing/Insights costs apply. Removing the connection removes its upload policy and managed selectors from regenerated Terraform; review existing published versions separately. Local tests evaluate policies and filters, validate provider schemas, and check dependency graphs without deploying AWS resources.
