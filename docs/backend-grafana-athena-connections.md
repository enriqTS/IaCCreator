# Managed Grafana Athena connections

Managed Grafana → Athena (`queries`) requires existing `database_name` and `table_name` selectors. `GrafanaAthenaConfig` exposes both through `/api/connection-schemas`; names use lowercase ASCII letters, digits, and underscores, with a letter or underscore first and a maximum of 255 characters. Each binding selects one table in the workgroup Region's default `AwsDataCatalog`. Connect all tables needed by joins or views. Catalog objects, data ingestion, source S3 access, Lake Formation grants, and encryption-key permissions remain separately configured.

The workgroup must enforce its result configuration and have one concrete, nonempty S3 prefix ending in `/`. Configure `output_location`, for example `s3://query-results/grafana/results/`, or connect Athena → S3 (`stores_results`) with `prefix: grafana/results`. A managed result location overrides the external field. Prefix segments start with a letter, digit, underscore, or hyphen and may subsequently include dots; wildcards, interpolation, URI query strings, empty segments, and bucket-root locations are rejected. Workgroups without a Grafana connection retain their existing behavior. See [Athena result-location precedence](https://docs.aws.amazon.com/athena/latest/ug/query-results-specify-location.html).

`GrafanaAthenaSource` contributes to the shared workspace-owned customer-managed data-source role. Athena exports its native ARN/name, ARN-derived Region, result URI, and enforcement setting; a typed `athena_tables` input carries those values and the selected database/table names into Grafana. Native Terraform preconditions verify ARN/name/Region consistency, matching account/partition, selectors, and enforced result-prefix settings. Same-account cross-Region workgroups are supported. Athena outputs depend on native workgroup resources, including their managed result-location input, and contain no Grafana dependencies.

The policy grants `GetWorkGroup`, `StartQueryExecution`, `GetQueryExecution`, `GetQueryResults`, and `StopQueryExecution` on exact connected workgroup ARNs. These permissions cover executions by other users in those workgroups as well. Metadata APIs use the regional `AwsDataCatalog` ARN. `ListDataCatalogs` and `ListWorkGroups` require wildcard resources, restricted by `aws:RequestedRegion` to connected Regions; discovery can reveal unrelated names. Administrative, prepared/named query, notebook, and federated Lambda invocation actions receive no grants. See the [Athena authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_athena.html).

Glue read grants name exact selected table ARNs and their database/catalog ancestors, including table partition reads. The generated policy grants no Glue creation, updates, or deletion. Table authorization covers all partitions; connect view/join dependencies separately. See [Glue resource authorization for Athena](https://docs.aws.amazon.com/athena/latest/ug/fine-grained-access-to-glue-resources.html).

Result storage grants `GetBucketLocation`, `ListBucket`, and `ListBucketMultipartUploads` on exact result bucket ARNs. Listings are bucket-wide and can reveal other key names. `GetObject`, `PutObject`, `AbortMultipartUpload`, and `ListMultipartUploadParts` apply only under the enforced result prefix. This permits reading other executions' results and writing objects within that prefix; object deletes and dataset object reads receive no grants. Use a dedicated result prefix rather than an ingestion prefix. Existing bucket policies and other identity grants may broaden or deny access. External result buckets need matching Region and owner authorization; encrypted result/data buckets and encrypted catalog metadata need separate KMS permissions. See [Athena S3 access requirements](https://docs.aws.amazon.com/athena/latest/ug/federated-query-iam-access.html).

IAM `StartQueryExecution` does not filter SQL to `SELECT`. The generated role omits catalog mutations and dataset writes, but permissions to write result objects can also support operations such as an `UNLOAD` into that prefix. Additional external grants can broaden SQL capabilities. SQL reviews, dataset authorization, and workload/cost controls remain external; this is a scoped execution role, not a SQL statement firewall.

The Grafana module exports `athena_data_sources`, keyed by `<workgroup-node-name>:<database-name>`. Multiple table bindings in one database produce one payload. Each payload uses `grafana-athena-datasource`, proxy access, default AWS role credentials, the native Region/workgroup/result location, `AwsDataCatalog`, and the selected database. Result reuse is disabled by default. The plugin has no configured default table field; tables are authorized bindings and selected in the query editor or SQL. UIDs derive from the native workgroup ARN and database, so node renames preserve identity. Display names are capped at 190 characters with a binding-specific hash; selectors and output keys retain their full values. No passwords, keys, tokens, or custom API endpoints are exported. See [plugin configuration](https://grafana.com/docs/plugins/grafana-athena-datasource/latest/configure/) and its [query implementation](https://github.com/grafana/athena-datasource/blob/main/pkg/athena/api/api.go).

Install an Athena plugin compatible with the workspace's Grafana version, provision the catalog tables and result bucket, and supply dataset/KMS/Lake Formation permissions to the exported `data_source_role_arn`. Apply the settings using an authorized Grafana identity. For workspace `grafana`, workgroup node `queries`, and database `application`, run from the generated environment directory:

```sh
terraform output -json grafana > grafana-outputs.json
jq '.athena_data_sources["queries:application"]' grafana-outputs.json > athena-data-source.json
```

Submit the JSON to `POST https://<workspace_endpoint>/api/datasources`, or update with `PUT /api/datasources/uid/<uid>`. Use Save & test, then query a selected table to verify source-data access. Grafana objects, dashboards, user access, network reachability, and table lifecycle remain operational tasks. Custom/federated catalogs, Athena-managed result storage, and IAM Identity Center trusted identity propagation are unmodeled.
